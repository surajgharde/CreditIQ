# ⚡ CreditIQ AI

## CreditIQ – AI-Powered Credit Risk & Fraud Detection System

An automated credit appraisal engine for the Indian mid-market / MSME lending
sector. It ingests messy financial documents, flags fraud signals, scores
default risk with an explainable model, and drafts a Credit Appraisal
Memorandum (CAM) as a formatted PDF.

> **Status: prototype.** This is a hackathon-grade demonstrator, not a
> production lending system. It has not been assessed against RBI or any other
> regulatory framework, and several screens are backed by seeded demo data
> rather than live computation. Do not use it to make real credit decisions.

---

## 💡 Problem Statement

Indian lenders write off large volumes of MSME credit every year — often not for
lack of data, but for lack of tooling to reconcile messy filings, surface fraud
signals, and document the reasoning behind a decision.

---

## ⚙️ Features

- 📄 **Document processing (OCR):** Extracts financial data from PDFs and
  images via pdfplumber / PyMuPDF, with Tesseract and AWS Textract for scanned
  or low-quality pages.
- 🔍 **Fraud detection:** Graph analysis (NetworkX) over counterparty flows to
  flag circular transactions and related-party patterns, plus GST
  reconciliation checks.
- 📊 **Risk scoring:** An XGBoost classifier over 12 financial and risk
  features produces a Probability of Default and an indicative rate.
- 🧠 **Explainability (SHAP):** TreeExplainer waterfall charts showing the
  per-feature contribution behind each score.
- 🚨 **Early Warning System:** A WebSocket dashboard that surfaces portfolio
  drift from sentiment, bank-flow and GST signals. Drift is **simulated**, not
  computed from live portfolio data.
- 📑 **Automated CAM:** Generates a 15-20 page Credit Appraisal Memorandum PDF
  with table of contents, 18 numbered sections, fixed tables and four data
  annexures (see *The CAM generator* below).
- 💬 **Multilingual assistant:** In-app chat panel that explains risk scores,
  fraud signals and CAM output in **English, Hindi or Marathi**, backed by the
  Mistral chat completions API (`POST /api/chat`). Falls back to canned replies
  when no key is configured.
- 🌐 **Multilingual input:** Language detection and translation on the document
  ingest path (English / Hindi / Marathi).
- 🤖 **Telegram bot:** Query analyses and decisions from Telegram. Each chat is
  linked to one company from the Profile page and is answered only about that
  company (see *The Telegram bot* below).

## 🛠️ Technology Stack

### Frontend
- **React 19 + TypeScript + Vite** — application shell and build tooling.
- **React Router** — routing.
- **Framer Motion** — transitions and animation.
- **Lucide React** — icon set.
- Styling is hand-written CSS and inline styles (no utility-CSS framework).
  Charts are server-rendered SHAP images from matplotlib, not a client-side
  charting library.

### Backend
- **FastAPI** — API and async orchestration, with native WebSockets for EWS.
- **Pandas / NumPy** — structuring and aggregating extracted tabular data.
- **SQLAlchemy** — ORM layer.

### Databases
- **SQLite** — the default store; used automatically when `DATABASE_URL` is
  unset.
- **PostgreSQL** — optional, enabled by pointing `DATABASE_URL` at an instance.
- **ChromaDB** — vector store backing the RAG lookups over textual reports.
- **Redis** — optional cache for scoring results and EWS telemetry. The app
  degrades gracefully when it is unavailable.

### AI / ML
- **XGBoost** — gradient-boosted classifier producing the Probability of
  Default.
- **SHAP** — model explainability via waterfall diagrams.
- **Scikit-learn** — preprocessing and train/test splitting.
- **FinBERT** (via `transformers`) — financial sentiment scoring over retrieved
  news. Loaded lazily to reduce memory use.
- **ChromaDB + sentence-transformers** — embedding and retrieval for the RAG
  context assembled into the CAM prompt.
- **NetworkX** — graph analysis for circular-transaction and shell-company
  detection.
- **Cohere Command R** (`command-r-08-2024`) — synthesizes the CAM narrative.
- **ReportLab** — lays the generated narrative out into the final PDF.
- **Mistral** (`mistral-small-latest` by default) — powers the multilingual
  chat assistant, called over REST. Override with `MISTRAL_MODEL`.

### AI / LLM usage — what actually runs

The CAM narrative is generated by **Cohere Command R**
(`command-r-08-2024`), called from `backend/services/cam_service.py`. A RAG
context is assembled from the analysis record and passed as the prompt; the
response is laid out into a PDF by ReportLab.

An Anthropic client exists in `backend/services/external_apis.py`
(`call_claude`), but it is **not currently wired into the pipeline** — no code
path invokes it. `CLAUDE_API_KEY` is therefore optional and unused.

### The chat assistant

`POST /api/chat` takes `{ message, lang, history }` where `lang` is `en`, `hi`,
`mr`, or `auto`. The server pins the reply language in the system prompt rather
than trusting the model to mirror the input, because Hindi and Marathi share the
Devanagari script and are easily conflated. `auto` uses a marker-based
heuristic; the UI's language selector is the reliable path.

**Grounding in a borrower's file.** Pass `analysis_id` and the assistant is
given that borrower's record — decision, PD, recommended facility and rate,
fraud signals with their evidence amounts, extracted statement lines and derived
ratios, SHAP attribution, adverse media, and the decision reasoning — and
answers from it, quoting the real figures. The Dashboard passes the analysis it
is showing, so questions like "why was this flagged?" are answered about that
company. Without `analysis_id` the assistant has no borrower data and can only
explain how the platform works in general; that was the original behaviour and
is why answers used to be generic.

The prompt forbids stating any figure not in the file, and forbids inventing a
derivation the file does not record — a fabricated mechanism is treated as being
as serious as a wrong number. Ratios that could not be derived are listed
explicitly so the assistant says "not captured" instead of estimating.

`GET /api/chat/health` reports whether a key is configured, without revealing
it.

Mistral is called over plain REST with `requests` rather than the official SDK:
it is a heavy dependency for a single POST, and installing it here pulled in
packages that clash with ChromaDB's pins. A 429 from Mistral's free tier is
surfaced to the caller as a 429 with a "try again" message rather than a
generic upstream failure.

### The CAM generator

`command-r-08-2024` caps a single response at roughly 4k output tokens — about
six A4 pages — so a long memorandum cannot come from one call. Each of the 17
narrative sections is generated by its own request (run concurrently, bounded by
`CAM_CONCURRENCY`, default 4) and assembled by ReportLab alongside:

- a cover page and a table of contents with resolved page numbers
- six figures (see *Charts* below)
- a deterministic key-facts table driven straight from the analysis payload
- fixed tables for ratio, verification, group and compliance sections
- four annexures (SHAP attribution, fraud signals, adverse media, conditions)
  built entirely from the payload, with no model involvement
- conditions for approval inserted verbatim, never model-rewritten

**Charts.** Six figures are rendered with matplotlib and embedded as images:

| Figure | Section | Form | Why that form |
| --- | --- | --- | --- |
| 1.1 Risk position | Executive summary | Band strip with a marker | PD is one number, so a hero value on labelled risk bands rather than a chart implying a trend |
| 4.1 Facility | Facility structure | Two bars | Requested against recommended, with the haircut stated |
| 5.1 Financial position | Financial review | Horizontal bars, one hue | Magnitude across statement lines; single series needs no legend |
| 6.1 Ratios vs benchmark | Ratio analysis | Indexed bars, diverging | See note below |
| 12.1 Fraud signals | Fraud findings | Bars, status colours | Evidence amount per signal, risk level written beside each bar |
| 14.1 SHAP attribution | Explainability | Diverging bars about zero | Polarity: which factors push PD up and which pull it down |

Figure 6.1 plots each ratio **indexed to its own sector benchmark** (1.00x = at
benchmark) rather than side by side with it. Raw values put a percentage
(EBITDA margin, ~16) and three multiples (~0.4 to ~5) on one linear axis, which
squashed the multiples to unreadable stubs; the absolute figures stay in
Table 6.1 beside it. Colour marks whether the variance is *favourable*, which is
not the same as "above benchmark" — a high debt/equity is adverse while a high
current ratio is favourable — so the direction is set per ratio.

Every builder returns nothing when its inputs are absent, so a thin borrower
file produces fewer figures rather than an empty or invented chart.

Colour follows one validated palette: categorical hues in fixed order, a single
hue for magnitude, the blue/red diverging pair with a neutral midpoint for
polarity, and reserved status colours for risk state. Status colours always
appear beside a written level (CRITICAL/HIGH/MEDIUM/LOW), because two of them
sit close enough in the light band that hue alone would not separate them.

**Rate limits matter here.** A Cohere **Trial** key allows 20 API calls per
minute and one CAM needs 17, so an unthrottled run sits on the ceiling — any
retry, or a second CAM in the same minute, returns 429 and loses whole sections.
A process-wide limiter spaces calls to `CAM_RATE_LIMIT_PER_MIN` (default 15) and
429s back off for the rest of the window rather than retrying immediately. On a
Trial key expect roughly one CAM per minute; raise the limit only on a
Production key.

Length is governed by `CAM_SECTION_WORDS` (default 175). Measured page counts
for a complete borrower file:

| Model output vs requested length | Pages |
| --- | --- |
| 30% short | 16 |
| as requested | 18 |
| 30% long | 19 |

A **thin** file — no extracted financials, no fraud signals, no SHAP
attribution — comes out at about 13 pages, because four of the six figures have
nothing to plot and are omitted. That is deliberate: the alternative is padding
the memo or inventing charts, and a borrower with less on file genuinely has
less to appraise. Raise `CAM_SECTION_WORDS` if you need a longer floor;
roughly 30 words per section equals one page, and the ceiling moves with it.
`CAM_MODEL` overrides the model.

Figures the payload does not contain are printed as "Not extracted" rather than
estimated — the section prompts treat a fabricated number as a defect and an
acknowledged gap as required.

**Extracted financials.** The OCR step writes the statement lines it found to
`backend/data/financials_<id>.json` (gitignored — it holds real borrower data),
and the CAM router threads them into the payload as `financials`. They drive:

- Table 5.1, an extracted financial position statement with the OCR confidence
  and how many of the 14 statement lines were recovered
- Table 6.1, which compares each derived ratio against the sector benchmark and
  labels the variance favourable or adverse
- the applicant column of the group analysis table, and revenue plus
  facility-to-revenue in the key-facts table

`ocr_service` derives `current_ratio`, `interest_coverage`, `tol_tnw` and
`gross_profit_margin_percent` alongside the ratios it already computed. A ratio
is emitted only when its inputs were actually extracted, so a missing key reads
downstream as "not extracted" instead of being silently defaulted.

**Scanned documents need an OCR engine.** A PDF with no text layer goes to
Tesseract, falling back to AWS Textract. If neither is available the extraction
recovers nothing, and the analysis now **stops with an actionable error** rather
than proceeding — previously it continued and produced a credit decision built
entirely from `scoring_service`'s fallback ratio constants. Install Tesseract
and put it on PATH, or set valid AWS credentials.

**Known extraction limit.** Current assets and current liabilities are only read
from an explicit total line. Statements that list components without a total
(Inventories / Receivables / Cash / Other) leave both unextracted, so the
current ratio and DSCR are reported as not extracted. Summing component rows is
not yet implemented.

DSCR and `revenue_growth_percent` still cannot be derived — the first needs a
debt-service schedule and the second needs prior-year revenue, neither of which
is extracted. Both are labelled as such rather than estimated.

If a section request fails it is retried once; a failed section is marked in the
document and listed in `sections_failed` on the response. Generation aborts only
if more than half the sections fail.

### The Telegram bot

`/api/telegram/webhook` receives updates in production;
`backend/telegram_bot.py` long-polls the same handler for local development,
where there is no public HTTPS URL. Run only one of the two — Telegram permits a
single delivery method, and the poller clears any registered webhook on startup.

```bash
cd backend
python telegram_bot.py
```

**Only one poller may run at a time.** Telegram permits a single `getUpdates`
consumer per bot; a second one makes the two race, Telegram returns 409 Conflict
to the loser, and in the gaps between retries both deliver — so every message
gets answered twice. The script takes an exclusive lock
(`backend/.telegram_bot.lock`) and refuses to start if another instance holds
it. Note the running process keeps the code and `.env` it started with, so a
provider or key change needs a restart of both this and the backend.

Commands: `/list`, `/status <id>`, `/decision <id>`, `/ask <question>`,
`/whoami`, `/help`.

`/ask` from a company-linked chat is grounded in that borrower's latest analysis
and answers with its real figures. The company is passed to the chat endpoint as
a SQL scope, so the file is loaded with a `company_id` filter — a linked chat
cannot reach another borrower's record even if the model is talked into trying.
(Earlier this only appended the company *name* to the question, which gave the
model nothing to answer from.)

**Access control** is two-tier and default-deny. A Telegram bot can be messaged
by anyone who knows its handle, so nothing is served without an explicit grant:

| Chat kind | Granted by | Sees |
| --- | --- | --- |
| Company-linked | **Profile page** → Telegram chat access | Only the company it is linked to |
| Operator | `TELEGRAM_ALLOWED_CHAT_IDS` in `.env` | Every company |
| Anything else | — | Nothing |

A company-linked chat is confined in SQL: `/list` returns only that company's
analyses, and `/status`/`/decision` filter on `company_id`, so asking for
another borrower's analysis id returns "No analysis #N available to you" —
deliberately the same wording whether the id is absent or belongs to someone
else, since a different message would confirm it exists.

`/whoami` stays open to everyone so a contact can report their own ID; it
reveals nothing about any borrower.

**Linking a chat.** Profile → *Telegram chat access*: paste the chat ID, choose
the company, and optionally label the contact. The contact gets the ID by
sending `/whoami` to the bot. Re-submitting an existing chat ID re-points it
rather than adding a second row, so a chat can never resolve to two companies.
Links can be disabled without deleting, and *Send test* confirms the ID is
right — note a bot cannot message someone who has never written to it first,
which is the usual cause of a failed test.

Company-linked chats also get `/latest`, which returns their most recent
assessment without needing an id.

Set `TELEGRAM_WEBHOOK_SECRET` whenever you use the webhook: the endpoint is
public, and the secret is checked against the header Telegram sends. The webhook
returns 200 even when handling fails, because a non-200 makes Telegram retry the
same update indefinitely.

Replies carry a prototype disclaimer, and any analysis whose data quality score
is zero is flagged as resting on fallback constants rather than real statements.

### Pre-trained models

`backend/models/xgboost/` ships pre-trained `.pkl` models so a fresh clone can
score without credentials. These six files are currently **identical copies of
one base model** — per-sector differentiation is not yet real, despite the
filenames. Re-training from the Kaggle *Home Credit Default Risk* dataset
(which requires `KAGGLE_USERNAME` / `KAGGLE_KEY`) is only triggered if
`xgboost_creditiq_model.pkl` is missing.

## 🔑 Configuration

Copy the template and fill in what you need:

```bash
cp backend/.env.example backend/.env
```

`backend/.env` is gitignored — never commit it.

| Variable | Required for | Notes |
| --- | --- | --- |
| `COHERE_API_KEY` | CAM generation | Without it, CAM generation raises. Everything else works. |
| `MISTRAL_API_KEY` | Chat assistant | Without it, `/api/chat` returns 503 and the UI uses canned replies. |
| `CAM_SECTION_WORDS` / `CAM_CONCURRENCY` / `CAM_RATE_LIMIT_PER_MIN` / `CAM_MODEL` | CAM tuning | Optional. Defaults 175 / 3 / 15 / `command-r-08-2024`. |
| `TELEGRAM_BOT_TOKEN` | Telegram bot | From @BotFather. Without it the bot is inert and `/api/telegram/*` returns 503. |
| `TELEGRAM_ALLOWED_CHAT_IDS` | Telegram operator chats | Comma-separated numeric chat IDs that see every company. Company-scoped access is granted in the Profile page instead, not here. |
| `TELEGRAM_WEBHOOK_SECRET` | Telegram webhook | Required when using the webhook rather than the poller. |
| `JWT_SECRET` | Auth tokens | Any long random string. |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | Scanned-PDF OCR | Falls back to Tesseract when absent. |
| `NEWS_API_KEY` | Adverse-media retrieval | News risk degrades to a neutral score without it. |
| `KAGGLE_USERNAME` / `KAGGLE_KEY` | Re-training only | Not needed; trained models are committed. |
| `GSTN_*`, `MCA_*`, `TWILIO_*`, `SENDGRID_*`, `REDIS_URL` | Optional integrations | Each degrades gracefully. |

## 🏁 Running Locally

Two terminals.

**Terminal 1 — Backend:**

```bash
cd backend
python -m venv venv

# Windows
.\venv\Scripts\activate
# macOS/Linux
source venv/bin/activate

pip install -r requirements.txt
python run_backend.py
```

✅ Backend: `http://localhost:8000` · 📖 API docs: `http://localhost:8000/docs`

**Terminal 2 — Frontend:**

```bash
cd frontend
npm install
npm run dev
```

✅ Frontend: `http://localhost:5173`

### Quick start scripts

From the repository root:

```bash
python start_backend.py          # either platform
```

```powershell
.\start_frontend.ps1             # Windows
```

```bash
bash start_frontend.sh           # macOS/Linux
```

### Default login

The prototype seeds a single administrator account on first run. The
credentials are defined in `backend/routers/auth.py` — **change them before
exposing this anywhere**, and replace the hardcoded check with real user
storage before any non-local deployment.
